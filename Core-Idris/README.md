# Core-Idris

Core-Idris uses Idris 2 dependent types for bounded frames and checked timing-window propositions, with libsodium and POSIX C interfaces for cryptography and operating-system resources. These checks do not constitute a proof of the C implementation, operating system, deployment, or the entire network protocol.

## Implemented controls

- Ed25519 verification, SHA-256, cryptographic random bytes, and AES-256-GCM. Invalid input, allocation failure and unsupported AES hardware return errors. There are no zero-filled success fallbacks or unchecked Idris pointer casts.
- Timing validation proves the circular distance is within the configured tolerance; negative timestamps and a tolerance covering the entire period are rejected. Timing is a filter, not authentication.
- Strict JSON rejects duplicate decoded keys, malformed escapes, floats, trailing data, non-portable integers and excessive size/depth. Request and trust schemas reject unknown fields.
- `--authorize` verifies a bounded signed request against an owner-controlled trust file. Grants require the intersection of build configuration, requested level, Mod level, capabilities and domain policy. Signatures cover both domain labels and the payload hash in sorted portable JSON. The old delimiter/hash/padding signature representation is not supported.
- Requests expire outside a 300-second window. An owner-only, locked and bounded replay ledger is flushed before a grant is returned. Full, locked or corrupt ledgers reject requests; live entries are never evicted. Keep the ledger directory owner-controlled and persistent across restarts; owner-initiated deletion or restoration from an old snapshot invalidates replay protection.
- Secret files are opened without following the final symlink, checked for owner/mode `0600`, regular type, single link and size, then checked again after reading. Callers receive the content read through that descriptor rather than reopening a validated path.
- Real nonblocking sockets use generation handles, a process-wide 512-socket limit, loopback-only binding, bounded backlog and explicit close. Build and context capability checks precede socket operations. Shutdown closes owned sockets and rejects later creation.
- Mutable buffer allocation is bounded per request and accounted in the caller's context. `secureZero` wipes the supplied buffer. Immutable Idris vectors/strings and copies managed by the runtime cannot be promised secure erasure; context accounting assumes trusted callers preserve the returned context.

## Commands and scope

`--feature-report` reports the build contract. Default L0 builds disable Crosed, application transport and domain-policy options. `make idris-crosed-variant` produces the explicit L5 variant and restores the L0 default binary.

`--authorize REQUEST_FILE TRUST_FILE` validates an offline Crosed grant. Both files must meet the private-file rules. The exact schemas are in `src/Shadow6/Documents.idr`; a signed example and rejection tests are generated by `test_security.py`. Security documents use ASCII JSON; escaped Unicode is parsed, while signed identities and domain labels use constrained ASCII names.

`--loopback-test` and `--udp-loopback` remain diagnostics. The native data plane is an explicitly configured, fixed-peer UDP agent/client relay:

```sh
# Create and distribute this out of band; never pass it on the command line.
umask 077; head -c 32 /dev/urandom > idris-native.key
shadow6-idris --native-agent 0.0.0.0 41001 CLIENT_IP 41000 127.0.0.1 9000 idris-native.key 100000
shadow6-idris --native-client 0.0.0.0 41000 AGENT_IP 41001 8000 idris-native.key 100000
```

The client exposes UDP port 8000 only on loopback and the agent forwards only to the fixed numeric target. Each datagram is 1–1024 bytes and uses a direction-bound, sequence-numbered XChaCha20-Poly1305 frame. A fresh 128-bit sender session is authenticated and included in nonce derivation on every process start; the receiver pins the first authenticated session. It also pins the configured source IP/port and rejects unknown versions, directions, sizes, peers, in-process replay, excessive sequence gaps and authentication failures. The 32-byte key file must be a current-user-owned, non-symlink, single-link regular file of mode `0600`; it is rechecked after reading. Idle relays stop after 30 seconds and packet limits are mandatory.

This legacy path is UDP, not a reliable stream, and supports one fixed
client/target pair per process. It remains available unchanged through the
`--native-client`/`--native-agent` commands. Use a unique master key per link
and rotate it before restart when cross-restart replay is in the threat model.
The optional companions provide message segmentation, retransmission and
logical streams; neither companion supplies durable replay state across
restarts. Native roles remain usable without either companion.

The new native three-role mode authenticates fresh X25519 exchanges with pinned
Ed25519 identities (`S6I2`) and derives the data key from the handshake and a
deployment binding. Start broker, agent, then client:

```sh
shadow6-idris --chain broker 127.0.0.1 41000 127.0.0.1 41002 127.0.0.1 41004 broker.pins 1000000
shadow6-idris --chain agent 127.0.0.1 41004 127.0.0.1 41000 127.0.0.1 9000 agent.keys 1000000
shadow6-idris --chain client 127.0.0.1 41002 127.0.0.1 41000 127.0.0.1 8000 client.keys 1000000
```

Each configuration is a 96-byte owned, mode-0600, non-symlink regular file.
Endpoint files contain own Ed25519 seed, pinned remote endpoint public key,
and a shared random 32-byte deployment binding. The broker file contains 32
zero reserved bytes, client public key, agent public key. The broker validates
the signed hello and challenge-bound reply and forwards ciphertext between
the exact configured peers; it never receives an endpoint private/data key.
The application listener remains loopback-only. Other bind/peer IPv4 addresses
must be explicitly configured; host network policy remains the operator's job.

All three roles are bounded to five minutes and one million loop iterations;
the explicit limit additionally bounds endpoint transactions/broker forwarded
frames. Admission expires after five seconds, broker inactivity after 60
seconds and endpoint inactivity after 30 seconds. Application datagrams remain
1..1024 bytes; this is one fixed route, without native retransmission or
multi-client multiplexing. Protocols remain family-specific.

The shared `integration/stack_test.py --engine shadow6-idris --benchmark`
evaluates native, Python and Node.js paths. Actions builds the Idris executable
and runs this matrix plus concurrent pressure and broker rejection tests.
Local `test_security.py` independently compiles/tests only the C FFI boundary,
including a real signed three-role transaction; that is not an Idris build.

The feature schema aligns with the other Cores, but it is not evidence of wire compatibility. Qubes-inspired labels do not replace qrexec/VM/hypervisor isolation.

## Build and verification

Requirements: Idris 2 (CI uses 0.8), Chez, libsodium, a C11 compiler, pthreads, Make and Python 3. Build with `make core-idris`; run feature-contract tests with `make test-idris`.

The manually dispatched `Idris security regressions` GitHub Actions workflow checks modules, builds default and Crosed variants, and runs executable regressions on Linux and macOS. During the current audit, Idris compilation and execution are restricted to that job at the operator's request.

`python3 Core-Idris/test_security.py` locally compiles only the C interface into a temporary directory and tests its failure paths plus a real encrypted client→agent→echo→client transaction. With `IDRIS_SECURITY_BINARIES=1`, the same harness additionally tests both Idris executables and signed authorization across process restarts. `--native-self-test` verifies framing, direction separation, replay and tamper rejection; `--security-test` exercises strict parsing, real timing proofs, replay capacity, SHA-256, allocation and buffer wiping.
